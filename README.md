# Events API

REST API для управления событиями и бронированиями на ASP.NET Core (.NET 10). Данные хранятся в PostgreSQL; доступ к ним выполняется через Entity Framework Core и провайдер Npgsql.

## Структура проекта

| Каталог / файл | Назначение |
| :--- | :--- |
| `Controllers/` | HTTP-эндпоинты событий и броней |
| `Services/` | Логика создания и изменения событий и броней |
| `Repositories/` | Интерфейсы и реализации доступа к данным |
| `DataAccess/` | `AppDbContext`, конфигурации сущностей и миграции |
| `Models/`, `DTOs/` | Сущности и контракты запросов и ответов |
| `Background tasks/` | Фоновая обработка ожидающих броней |
| `Middlewares/`, `Exceptions/` | Обработка ошибок |
| `Test/` | Тесты на InMemory и Moq |
| `Integration tests/` | Интеграционные тесты репозиториев на PostgreSQL |
| `Program.cs` | DI, применение миграций, начальные данные и запуск API |
| `docker-compose.yml` | Локальная база PostgreSQL; приложение запускается отдельно через .NET |
| `dotnet-tools.json` | Манифест локального инструмента `dotnet-ef` |

## Запуск приложения

### Шаг 1. Предварительные требования

Для запуска нужны **.NET SDK 10.0** и работающий сервер **PostgreSQL**. В репозитории настроен PostgreSQL 16 через Docker Compose; для этого варианта также нужен Docker с Compose.

Проверить версию можно командой в терминале:
```bash
dotnet --version
```

### Шаг 2. Клонирование и переход в папку проекта

```bash
git clone <ссылка_на_ваш_репозиторий>
cd "<папка_репозитория>"
```

### Шаг 3. Запуск PostgreSQL

Из корня репозитория запустите базу:

```bash
docker compose up -d postgres
docker compose ps
```

Дождитесь состояния `healthy`. Файл `docker-compose.yml` задаёт базу `eventapi`, пользователя `postgres`, пароль `postgres` и порт `5432`. Данные сохраняются в именованном томе `eventapi_pgdata`. Вместо контейнера можно использовать отдельно установленный PostgreSQL.

### Шаг 4. Настройка строки подключения

В `appsettings.json` задайте `ConnectionStrings:DefaultConnection`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
}
```

Эти значения соответствуют Docker Compose. Для своего сервера измените `Host`, `Port`, `Database`, `Username` и `Password`. Пользователю нужны права на создание и изменение объектов схемы для применения миграций; если база ещё не существует — также права на её создание.

Строку можно переопределить переменной окружения `ConnectionStrings__DefaultConnection`. Пример для PowerShell:

```powershell
$env:ConnectionStrings__DefaultConnection = "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=your_password"
```

### Шаг 5. Сборка и запуск приложения

Из папки решения выполните:

```bash
dotnet restore "Events API.sln"
dotnet build "Events API.sln" --no-restore
dotnet run --project "Events API.csproj" --launch-profile http
```

**Схема БД управляется миграциями EF Core.** После `builder.Build()` приложение создаёт DI scope, получает `AppDbContext` и вызывает `db.Database.Migrate()`. При запуске автоматически применяются ещё не выполненные миграции. Начальная миграция `InitialCreate` создаёт таблицы `events` и `bookings`, индекс по `bookings.event_id` и внешний ключ `bookings.event_id → events.id` с каскадным удалением. Имена столбцов используют `snake_case`. Выполненные миграции учитываются в таблице `__EFMigrationsHistory`.

Для первого запуска с новой базой отдельное применение миграций не требуется. Команды для изменения схемы и ручного применения описаны ниже.

Если таблица событий пустая, приложение добавляет тестовые данные с датами относительно времени запуска (UTC):

| Событие | Начало | Число мест |
| :--- | :--- | :--- |
| Рок-фестиваль | Через 1 день | 100 |
| Конференция .NET | Через 7 дней | 50 |
| Кулинарный мастер-класс | Через 14 дней | 10 |

При непустой таблице повторный запуск эти записи не добавляет. Остановить контейнер с сохранением данных можно командой `docker compose down`.

## Миграции EF Core

Исходники миграций и снимок модели находятся в `DataAccess/Migrations` и должны сохраняться в репозитории вместе с изменениями моделей. Вместо `EnsureCreated()` используется `Migrate()`; изменения моделей сами по себе не меняют схему — для них нужна новая миграция.

Все команды выполняются из корня репозитория. Сначала восстановите пакеты и локальный инструмент EF Core, версия которого зафиксирована в `dotnet-tools.json`:

```bash
dotnet restore "Events API.sln"
dotnet tool restore
```

После изменения модели или конфигураций создайте миграцию с описательным названием:

```bash
dotnet ef migrations add AddEventLocation --project "Events API.csproj" --output-dir DataAccess/Migrations
```

`AddEventLocation` — пример имени; замените его на название своего изменения. `InitialCreate` уже включена в проект, повторно создавать её не нужно. Проверьте сгенерированные операции `Up` и `Down` перед применением.

Применить все ожидающие миграции вручную:

```bash
dotnet ef database update --project "Events API.csproj"
```

Команда использует `ConnectionStrings:DefaultConnection`; базу PostgreSQL нужно предварительно запустить. При обычном запуске API тот же результат достигается автоматически через `db.Database.Migrate()`.

Показать список миграций и проверить, нет ли изменений модели без миграции:

```bash
dotnet ef migrations list --project "Events API.csproj"
dotnet ef migrations has-pending-model-changes --project "Events API.csproj"
```

Получить SQL для просмотра или отдельного применения:

```bash
dotnet ef migrations script --project "Events API.csproj" --output migrations.sql
```

### База, созданная прежней версией приложения

Ранее приложение использовало `EnsureCreated()` и таблицы `Events` и `Bookings`. Такая база не содержит истории миграций и автоматически не преобразуется в текущую схему `events` / `bookings`. Для локального запуска можно указать новую пустую базу через строку подключения. Если существующие данные нужно сохранить, сначала сделайте резервную копию и подготовьте отдельный перенос данных и согласование схемы; повторный запуск `InitialCreate` не выполняет этот перенос.

## Запуск тестов

В решении два тестовых проекта:

| Проект | Что проверяет | Требования |
| :--- | :--- | :--- |
| `Test/Test.csproj` | Сервисы, контроллер броней, модель брони и фоновую обработку; использует EF Core InMemory и Moq | .NET SDK 10; Docker и PostgreSQL не нужны |
| `Integration tests/Integration tests.csproj` | Все методы обоих репозиториев на настоящем PostgreSQL через Testcontainers | .NET SDK 10 и работающий Docker с Linux-контейнерами |

Тесты InMemory создают отдельную базу для каждого экземпляра тестового класса. Scoped-сервисы и репозитории получают зависимости из DI; параллельные запросы бронирования используют отдельные scope. Эти тесты проверяют сохранение между контекстами и защиту от превышения вместимости, но не SQL и ограничения PostgreSQL.

Интеграционные тесты автоматически запускают **один общий контейнер PostgreSQL `16-alpine`** на свободном порту и удаляют его после завершения. Оба класса входят в одну коллекцию xUnit и выполняются последовательно. Перед каждым тестом, включая каждый вариант `[Theory]`, вызываются `EnsureDeletedAsync()` и `MigrateAsync()`: база очищается и схема создаётся из миграций. Данные готовятся в каждом тесте самостоятельно, поэтому порядок запуска не влияет на результат.

Проверяются все сочетания фильтров событий, границы дат, регистронезависимый поиск, сортировка, пагинация и общее количество результатов, перечитывание сущностей, выборка ожидающих броней, сохранение статусов, внешний ключ, каскадное удаление и откат при ошибке вставки. Строка подключения получается из контейнера: тесты не используют базу приложения, а запуск Docker Compose для них не требуется. При первом запуске Docker загружает необходимые образы, поэтому нужен доступ к реестру образов.

Для запуска всех тестов из корня репозитория **сначала запустите Docker**:

```bash

```

Только тесты InMemory (без Docker):

## Получение списка событий: фильтрация и пагинация

Эндпоинт `GET /api/events` поддерживает следующие необязательные query-параметры:

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `title` | string | Поиск событий, в названии которых содержится указанная строка. Регистр не учитывается. |
| `from` | datetime | Нижняя граница даты начала: возвращаются события с `startAt >= from`. |
| `to` | datetime | Верхняя граница даты начала: возвращаются события с `startAt <= to`. |
| `page` | int | Номер страницы от `1` до `100`; по умолчанию — `1`. |
| `pageSize` | int | Число элементов на странице от `1` до `100`; по умолчанию — `10`. |

Фильтры можно комбинировать. После фильтрации события сортируются по возрастанию даты начала, затем применяется пагинация.

Пример запроса:

```http
GET /api/events?title=festival&from=2027-08-01T00:00:00Z&to=2027-08-31T23:59:59Z&page=1&pageSize=5
```

Ответ содержит список `items` и метаданные пагинации: `page`, `pageSize`, `totalItems`, `totalPages`.

## Модель события

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор события. |
| `title` | `string` | Название события. |
| `description` | `string \| null` | Необязательное описание события. |
| `startAt` | `datetime` | Дата и время начала события. |
| `endAt` | `datetime` | Дата и время окончания события. |
| `totalSeats` | `int` | Общая вместимость события. При создании должна быть больше нуля. |
| `availableSeats` | `int` | Число ещё доступных для бронирования мест. При создании равно `totalSeats`, уменьшается при резервировании и не передаётся клиентом в запросах. |

При изменении `totalSeats` через `PUT /api/events/{id}` уже зарезервированные места сохраняются: `availableSeats` пересчитывается с учётом новой вместимости. Нельзя установить вместимость меньше числа уже зарезервированных мест.

### Правила запросов

В `POST` и `PUT` передаются `title`, `startAt`, `endAt`, `totalSeats` и необязательное `description`. HTTP-валидация этих запросов требует название длиной не менее 5 символов. PostgreSQL ограничивает название 200 символами, описание — 500; превышение этих ограничений сейчас приводит к ошибке сохранения (`500`), отдельная HTTP-валидация максимальной длины не настроена.

Дата начала не должна быть в прошлом, дата окончания должна быть позже начала, а вместимость — больше нуля. Передавайте даты в UTC в формате ISO 8601 с суффиксом `Z`, включая параметры `from` и `to`: в PostgreSQL используется `timestamp with time zone`.

При создании события и изменении названия через `PATCH` сервис проверяет совпадение полного названия без учёта регистра и возвращает `409` при совпадении. При полном обновлении через `PUT` такая проверка сейчас не выполняется; уникальный индекс по названию в БД отсутствует.

Для изменения только названия используйте:

```http
PATCH /api/events/11111111-1111-1111-1111-111111111111
Content-Type: application/json

{
  "title": "Updated concert title"
}
```

## Бронирование события

Бронь создаётся для существующего события. Операция выполняется асинхронно: API сразу сохраняет бронь в статусе `Pending` и возвращает `202 Accepted`, а окончательная обработка выполняется в фоне.

### Модель брони

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор брони. |
| `eventId` | `guid` | Идентификатор события, для которого создана бронь. |
| `createdAt` | `datetime` | Время создания брони. |
| `processedAt` | `datetime \| null` | Время завершения фоновой обработки; до неё равно `null`. |
| `status` | `BookingStatus` | Текущее состояние обработки. |

Статусы `BookingStatus`:

| Значение | JSON-значение | Описание |
| :--- | :--- | :--- |
| `Pending` | `0` | Бронь создана и ожидает обработки. |
| `Confirmed` | `1` | Бронь успешно подтверждена. |
| `Rejected` | `2` | Бронь отклонена. Текущий фоновый обработчик не устанавливает этот статус при ошибке. |

### Эндпоинты броней

| Метод | Эндпоинт | Описание |
| :--- | :--- | :--- |
| **POST** | `/api/events/{eventId}/book` | Создать бронь в статусе `Pending`. Возвращает `202 Accepted`; если свободных мест нет — `409 Conflict`. |
| **GET** | `/api/bookings/{id}` | Получить бронь и её текущий статус. Возвращает `200 OK`. |

Для несуществующего события при создании и для несуществующей брони при получении возвращается `404 Not Found`.
Если все места уже зарезервированы, `POST /api/events/{eventId}/book` возвращает `409 Conflict` с сообщением `No available seats for this event`.

### Фоновая обработка

`BookingsService` резервирует место и создаёт бронь со статусом `Pending`. Один вызов `SaveChangesAsync()` сохраняет бронь и изменение `AvailableSeats`: оба объекта отслеживает один контекст. Статический `SemaphoreSlim(1, 1)` защищает создание броней между scoped-экземплярами сервиса внутри одного процесса.

`BookingBackgroundService` выбирает до 100 ожидающих броней по времени создания и обрабатывает их параллельно через `Task.WhenAll`:

1. Имитирует внешний вызов задержкой в 5 секунд.
2. Создаёт отдельный DI scope для каждой брони и заново загружает её из БД.
3. Пропускает удалённые брони и записи, чей статус уже отличается от `Pending`.
4. Подтверждает ожидающую бронь через `IBookingService` и сохраняет статус и время обработки.

При ошибке обработки отдельной брони обработчик пишет сообщение в журнал; бронь остаётся `Pending` для повторной попытки. При отсутствии ожидающих броней опрос повторяется через 100 мс. Брони в финальном статусе повторно не выбираются.

При удалении события связанные брони удаляются каскадно согласно обязательной связи EF Core.

### Пример использования

Сначала создайте событие и сохраните его идентификатор из ответа. Укажите будущие даты в UTC (суффикс `Z`):

```http
POST /api/events
Content-Type: application/json

{
  "title": "Summer concert",
  "description": "Open-air concert",
  "startAt": "2027-09-01T18:00:00Z",
  "endAt": "2027-09-01T21:00:00Z",
  "totalSeats": 100
}
```

Создайте бронь для полученного `eventId`:

```http
POST /api/events/11111111-1111-1111-1111-111111111111/book
```

Ответ содержит заголовок `Location: /api/bookings/{id}`, время создания и начальный статус `Pending`:

```json
{
  "id": "22222222-2222-2222-2222-222222222222",
  "eventId": "11111111-1111-1111-1111-111111111111",
  "createdAt": "2026-08-12T10:00:00Z",
  "processedAt": null,
  "status": 0
}
```

Проверьте статус по ссылке из `Location`:

```http
GET /api/bookings/22222222-2222-2222-2222-222222222222
```

До завершения фоновой операции ответ содержит `"status": 0`; примерно через 5 секунд после начала обработки при успешной имитации — `"status": 1`.

### Сценарий с попыткой овербукинга

Создайте событие вместимостью в одно место, передав `"totalSeats": 1`, и дважды отправьте запрос бронирования для его `eventId`. Первый запрос зарезервирует единственное место и вернёт `202 Accepted`. Второй запрос не создаст бронь и вернёт `409 Conflict`:

```http
POST /api/events/11111111-1111-1111-1111-111111111111/book
```

```json
{
  "status": 409,
  "detail": "No available seats for this event"
}
```

В пределах одного процесса приложения семафор сериализует создание броней и предотвращает бронирование сверх доступного числа мест. Синхронизация между несколькими запущенными экземплярами приложения этим семафором не обеспечивается.

## Формат ошибок

Для необработанных исключений используется единый JSON-формат `ProblemDetails`, основанный на стандарте Problem Details for HTTP APIs (RFC 7807). `ValidationException` возвращается со статусом `400`, `NotFoundException` — `404`, `ConflictException` и `NoAvailableSeatsException` — `409`, остальные необработанные исключения — `500`. Ошибка также записывается в журнал приложения.

Пример ответа:

```json
{
  "status": 400,
  "detail": "Описание ошибки"
}
```

Ошибки привязки запроса и проверки DTO возвращаются отдельно через `InvalidModelStateResponseFactory` со статусом `400`. Например, для `page=0`:

```json
{
  "message": "Validation errors",
  "errors": {
    "Page": ["The field Page must be between 1 and 100."]
  }
}
```

Текст сообщения может зависеть от культуры приложения. Этот ответ отличается от `ProblemDetails`, возвращаемого middleware для исключений.

## Доступ к данным

`AppDbContext` предоставляет `DbSet<Event> Events` и `DbSet<Booking> Bookings`. Доступ к данным инкапсулирован в `EventRepository` и `BookingRepository`, которые реализуют `IEventRepository` и `IBookingRepository`. `EventsService` и `BookingsService` обращаются к данным только через эти интерфейсы; проверка бизнес-правил остаётся в сервисах и моделях.

Контекст, оба репозитория и оба сервиса зарегистрированы в DI с временем жизни `Scoped`. В пределах одного scope репозитории используют общий контекст, поэтому создание брони и резервирование места сохраняются совместно. `BookingBackgroundService` получает репозиторий и сервис через `IServiceScopeFactory`, создавая отдельный scope для выборки и для каждой параллельно обрабатываемой брони.

Конфигурации в `DataAccess/Configurations` задают ключи, таблицы, обязательные поля и связь «одно событие — много броней» по `EventId`. Модели содержат навигационные свойства `Event.Bookings` и `Booking.Event`. Идентификаторы создаются приложением. Название события ограничено 200 символами, описание — 500. Статус брони хранится в PostgreSQL строкой, а в JSON API передаётся числом.

## Реализованные эндпоинты (CRUD)

| Метод | Эндпоинт | Описание |
| :--- | :--- | :--- |
| **GET** | `/api/events` | Получить список событий с фильтрацией и пагинацией |
| **GET** | `/api/events/{id}` | Получить детальную информацию о событии по ID |
| **POST** | `/api/events` | Создать новое событие (Возвращает `201 Created`) |
| **PUT** | `/api/events/{id}` | Полное обновление (замена) события |
| **PATCH**| `/api/events/{id}` | Частичное обновление (только `Title`) |
| **DELETE**| `/api/events/{id}` | Удаление события (Возвращает `204 No Content`) |
| **POST** | `/api/events/{eventId}/book` | Создать бронь и начать её фоновую обработку (`202 Accepted`, либо `409 Conflict`, если мест нет) |
| **GET** | `/api/bookings/{id}` | Получить бронь и статус её обработки |

## Решение проблем при запуске

| Симптом | Что проверить |
| :--- | :--- |
| `dotnet ef` не найден | Выполните `dotnet tool restore` из корня репозитория, где находится `dotnet-tools.json` |
| API не подключается к PostgreSQL | Проверьте `docker compose ps`, состояние `healthy`, порт `5432` и строку подключения; журнал БД доступен через `docker compose logs postgres` |
| Порт `5432` занят | Освободите порт или измените опубликованный порт в Compose и `Port` в строке подключения |
| Интеграционные тесты не подключаются к Docker | Запустите Docker, включите Linux-контейнеры и проверьте `docker version`; при первой загрузке образов проверьте доступ к реестру |
| Миграция завершается ошибкой на старой базе | Проверьте, была ли база создана через `EnsureCreated()`, и прочитайте раздел о переходе выше |
| Ошибка сохранения даты | Проверьте, что дата передана в UTC с суффиксом `Z` |
