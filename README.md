# Events API

REST API для управления событиями и бронированиями на ASP.NET Core (.NET 10). Данные хранятся в PostgreSQL; доступ к ним выполняется через Entity Framework Core и провайдер Npgsql.

---

## Запуск приложения

### Шаг 1. Предварительные требования
Для запуска нужны **.NET SDK 10.0** и работающий сервер **PostgreSQL**. В репозитории настроен PostgreSQL 16 через Docker Compose; для этого варианта также нужен Docker с Compose.

Проверить версию можно командой в терминале:
```bash
dotnet --version
```

### Шаг 2. Клонирование и переход в папку проекта
```bash
git clone <ссылка_на_ваш_репозиторий>
cd "Events-API" 
```

### Шаг 3. Запуск PostgreSQL

Из корня репозитория запустите базу:

```bash
docker compose up -d postgres
docker compose ps
```

Дождитесь состояния `healthy`. Файл `docker-compose.yml` задаёт базу `eventapi`, пользователя `postgres`, пароль `postgres` и порт `5432`. Данные сохраняются в именованном томе `eventapi_pgdata`. Вместо контейнера можно использовать отдельно установленный PostgreSQL.

### Шаг 4. Настройка строки подключения

В `appsettings.json` задайте `ConnectionStrings:DefaultConnection`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
}
```

Эти значения соответствуют Docker Compose. Для своего сервера измените `Host`, `Port`, `Database`, `Username` и `Password`. Пользователю нужны права на создание таблиц; если база ещё не существует — также права на её создание.

Строку можно переопределить переменной окружения `ConnectionStrings__DefaultConnection`. Пример для PowerShell:

```powershell
$env:ConnectionStrings__DefaultConnection = "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=your_password"
```

### Шаг 5. Сборка и запуск приложения

Из папки решения выполните:

```bash
dotnet run --project "Events API.csproj" --launch-profile http
```

После `builder.Build()` приложение создаёт DI scope, получает `AppDbContext` и вызывает `db.Database.EnsureCreated()`. **Схема БД создаётся автоматически при первом запуске**: в новой базе создаются таблицы `Events` и `Bookings` и связь между ними. Отдельный запуск миграций для первоначального старта не требуется. `EnsureCreated` не обновляет существующую схему при изменении моделей.

Если таблица событий пустая, приложение добавляет тестовые данные с датами относительно времени запуска (UTC):

| Событие | Начало | Число мест |
| :--- | :--- | :--- |
| Рок-фестиваль | Через 1 день | 100 |
| Конференция .NET | Через 7 дней | 50 |
| Кулинарный мастер-класс | Через 14 дней | 10 |

При непустой таблице повторный запуск эти записи не добавляет. Остановить контейнер с сохранением данных можно командой `docker compose down`.

## Запуск тестов

В решении есть тесты сервисов событий и броней, контроллера броней, модели брони и фоновой обработки. **В тестах используется InMemory-провайдер EF Core** (`Microsoft.EntityFrameworkCore.InMemory`); PostgreSQL и Docker для их запуска не нужны.

Тесты сервисов настраивают `ServiceCollection`, регистрируют `AppDbContext`, `IEventService` и `IBookingService` как scoped и получают зависимости из DI. Каждый экземпляр тестового класса создаёт отдельный провайдер с уникальным именем базы. Имя генерируется один раз **до** лямбды `UseInMemoryDatabase`, поэтому scope одного провайдера видят общие данные, а тесты изолированы друг от друга. Для каждого параллельного запроса бронирования создаётся отдельный scope и контекст. Проверяются сохранение данных между scope и защита от бронирования сверх вместимости.

Эти тесты не проверяют SQL-запросы и ограничения реального PostgreSQL.

Для запуска всех тестов из корневой папки решения:

```bash
dotnet test "Events API.sln"
```

Чтобы запустить только тестовый проект:

```bash
dotnet test "Test/Test.csproj"
```

## Получение списка событий: фильтрация и пагинация

Эндпоинт `GET /api/events` поддерживает следующие необязательные query-параметры:

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `title` | string | Поиск событий, в названии которых содержится указанная строка. Регистр не учитывается. |
| `from` | datetime | Нижняя граница даты начала: возвращаются события с `startAt >= from`. |
| `to` | datetime | Верхняя граница даты начала: возвращаются события с `startAt <= to`. |
| `page` | int | Номер страницы; по умолчанию — `1`. |
| `pageSize` | int | Число элементов на странице; по умолчанию — `10`. |

Фильтры можно комбинировать. После фильтрации события сортируются по возрастанию даты начала, затем применяется пагинация.

Пример запроса:

```http
GET /api/events?title=festival&from=2026-08-01T00:00:00&to=2026-08-31T23:59:59&page=1&pageSize=5
```

Ответ содержит список `items` и метаданные пагинации: `page`, `pageSize`, `totalItems`, `totalPages`.

## Модель события

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор события. |
| `title` | `string` | Название события. |
| `description` | `string \| null` | Необязательное описание события. |
| `startAt` | `datetime` | Дата и время начала события. |
| `endAt` | `datetime` | Дата и время окончания события. |
| `totalSeats` | `int` | Общая вместимость события. При создании должна быть больше нуля. |
| `availableSeats` | `int` | Число ещё доступных для бронирования мест. При создании равно `totalSeats`, уменьшается при резервировании и не передаётся клиентом в запросах. |

При изменении `totalSeats` через `PUT /api/events/{id}` уже зарезервированные места сохраняются: `availableSeats` пересчитывается с учётом новой вместимости. Нельзя установить вместимость меньше числа уже зарезервированных мест.

## Бронирование события

Бронь создаётся для существующего события. Операция выполняется асинхронно: API сразу сохраняет бронь в статусе `Pending` и возвращает `202 Accepted`, а окончательная обработка выполняется в фоне.

### Модель брони

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор брони. |
| `eventId` | `guid` | Идентификатор события, для которого создана бронь. |
| `createdAt` | `datetime` | Время создания брони. |
| `processedAt` | `datetime \| null` | Время завершения фоновой обработки; до неё равно `null`. |
| `status` | `BookingStatus` | Текущее состояние обработки. |

Статусы `BookingStatus`:

| Значение | JSON-значение | Описание |
| :--- | :--- | :--- |
| `Pending` | `0` | Бронь создана и ожидает обработки. |
| `Confirmed` | `1` | Бронь успешно подтверждена. |
| `Rejected` | `2` | Бронь отклонена. Текущий фоновый обработчик не устанавливает этот статус при ошибке. |

### Эндпоинты броней

| Метод | Эндпоинт | Описание |
| :--- | :--- | :--- |
| **POST** | `/api/events/{eventId}/book` | Создать бронь в статусе `Pending`. Возвращает `202 Accepted`; если свободных мест нет — `409 Conflict`. |
| **GET** | `/api/bookings/{id}` | Получить бронь и её текущий статус. Возвращает `200 OK`. |

Для несуществующего события при создании и для несуществующей брони при получении возвращается `404 Not Found`.
Если все места уже зарезервированы, `POST /api/events/{eventId}/book` возвращает `409 Conflict` с сообщением `No available seats for this event`.

### Фоновая обработка

`BookingsService` резервирует место и создаёт бронь со статусом `Pending`. Один вызов `SaveChangesAsync()` сохраняет бронь и изменение `AvailableSeats`: оба объекта отслеживает один контекст. Статический `SemaphoreSlim(1, 1)` защищает создание броней между scoped-экземплярами сервиса внутри одного процесса.

`BookingBackgroundService` выбирает до 100 ожидающих броней по времени создания и обрабатывает их параллельно через `Task.WhenAll`:

1. Имитирует внешний вызов задержкой в 5 секунд.
2. Создаёт отдельный DI scope для каждой брони и заново загружает её из БД.
3. Пропускает удалённые брони и записи, чей статус уже отличается от `Pending`.
4. Подтверждает ожидающую бронь через `IBookingService` и сохраняет статус и время обработки.

При ошибке обработки отдельной брони обработчик пишет сообщение в журнал; бронь остаётся `Pending` для повторной попытки. При отсутствии ожидающих броней опрос повторяется через 100 мс. Брони в финальном статусе повторно не выбираются.

При удалении события связанные брони удаляются каскадно согласно обязательной связи EF Core.

### Пример использования

Сначала создайте событие и сохраните его идентификатор из ответа. Укажите будущие даты в UTC (суффикс `Z`):

```http
POST /api/events
Content-Type: application/json

{
  "title": "Summer concert",
  "description": "Open-air concert",
  "startAt": "2027-09-01T18:00:00Z",
  "endAt": "2027-09-01T21:00:00Z",
  "totalSeats": 100
}
```

Создайте бронь для полученного `eventId`:

```http
POST /api/events/11111111-1111-1111-1111-111111111111/book
```

Ответ содержит заголовок `Location: /api/bookings/{id}`, время создания и начальный статус `Pending`:

```json
{
  "id": "22222222-2222-2222-2222-222222222222",
  "eventId": "11111111-1111-1111-1111-111111111111",
  "createdAt": "2026-08-12T10:00:00Z",
  "processedAt": null,
  "status": 0
}
```

Проверьте статус по ссылке из `Location`:

```http
GET /api/bookings/22222222-2222-2222-2222-222222222222
```

До завершения фоновой операции ответ содержит `"status": 0`; примерно через 5 секунд после начала обработки при успешной имитации — `"status": 1`.

### Сценарий с попыткой овербукинга

Создайте событие вместимостью в одно место, передав `"totalSeats": 1`, и дважды отправьте запрос бронирования для его `eventId`. Первый запрос зарезервирует единственное место и вернёт `202 Accepted`. Второй запрос не создаст бронь и вернёт `409 Conflict`:

```http
POST /api/events/11111111-1111-1111-1111-111111111111/book
```

```json
{
  "status": 409,
  "detail": "No available seats for this event"
}
```

В пределах одного процесса приложения семафор сериализует создание броней и предотвращает бронирование сверх доступного числа мест. Синхронизация между несколькими запущенными экземплярами приложения этим семафором не обеспечивается.

## Формат ошибок

Для необработанных исключений используется единый JSON-формат `ProblemDetails`, основанный на стандарте Problem Details for HTTP APIs (RFC 7807). `ValidationException` возвращается со статусом `400`, `NotFoundException` — `404`, `ConflictException` и `NoAvailableSeatsException` — `409`, остальные необработанные исключения — `500`. Ошибка также записывается в журнал приложения.

Пример ответа:

```json
{
  "status": 400,
  "detail": "Описание ошибки"
}
```

## Доступ к данным

`AppDbContext` предоставляет `DbSet<Event> Events` и `DbSet<Booking> Bookings`. Сервисы работают с ними напрямую: запросы и сохранение выполняются асинхронно, изменения фиксируются через `SaveChangesAsync()`. Прежние in-memory репозитории и их интерфейсы удалены. Контекст и оба сервиса зарегистрированы в DI как scoped; фоновый обработчик получает их через `IServiceScopeFactory`.

Конфигурации в `DataAccess/Configurations` задают ключи, таблицы, обязательные поля и связь «одно событие — много броней» по `EventId`. Модели содержат навигационные свойства `Event.Bookings` и `Booking.Event`. Идентификаторы создаются приложением. Название события ограничено 200 символами, описание — 500. Статус брони хранится в PostgreSQL строкой, а в JSON API передаётся числом.
