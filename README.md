# Events API

REST API для управления списком событий, построенное на платформе ASP.NET Core (.NET 10).

---

## Запуск приложения

### Шаг 1. Предварительные требования
Убедитесь, что у вас установлен **.NET SDK 10.0**.  
Проверить версию можно командой в терминале:
```bash
dotnet --version
```

### Шаг 2. Клонирование и переход в папку проекта
```bash
git clone <ссылка_на_ваш_репозиторий>
cd "Events-API" 
```

### Шаг 3. Сборка и запуск приложения
Запустите команду сборки и старта проекта из папки, где находится файл решения (`.sln`):
```bash
dotnet run
```

## Получение списка событий: фильтрация и пагинация

Эндпоинт `GET /api/events` поддерживает следующие необязательные query-параметры:

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `title` | string | Поиск событий, в названии которых содержится указанная строка. Регистр не учитывается. |
| `from` | datetime | Нижняя граница даты начала: возвращаются события с `startAt >= from`. |
| `to` | datetime | Верхняя граница даты начала: возвращаются события с `startAt <= to`. |
| `page` | int | Номер страницы; по умолчанию — `1`. |
| `pageSize` | int | Число элементов на странице; по умолчанию — `10`. |

Фильтры можно комбинировать. После фильтрации события сортируются по возрастанию даты начала, затем применяется пагинация.

Пример запроса:

```http
GET /api/events?title=festival&from=2026-08-01T00:00:00&to=2026-08-31T23:59:59&page=1&pageSize=5
```

Ответ содержит список `events` и метаданные пагинации: `page`, `pageSize`, `totalItems`, `totalPages`.

## Модель события

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор события. |
| `title` | `string` | Название события. |
| `description` | `string \| null` | Необязательное описание события. |
| `startAt` | `datetime` | Дата и время начала события. |
| `endAt` | `datetime` | Дата и время окончания события. |
| `totalSeats` | `int` | Общая вместимость события. При создании должна быть больше нуля. |
| `availableSeats` | `int` | Число ещё доступных для бронирования мест. При создании равно `totalSeats`, уменьшается при резервировании и не передаётся клиентом в запросах. |

При изменении `totalSeats` через `PUT /api/events/{id}` уже зарезервированные места сохраняются: `availableSeats` пересчитывается с учётом новой вместимости. Нельзя установить вместимость меньше числа уже зарезервированных мест.

## Бронирование события

Бронь создаётся для существующего события. Операция выполняется асинхронно: API сразу сохраняет бронь в статусе `Pending` и возвращает `202 Accepted`, а окончательная обработка выполняется в фоне.

### Модель брони

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор брони. |
| `eventId` | `guid` | Идентификатор события, для которого создана бронь. |
| `createdAt` | `datetime` | Время создания брони. |
| `processedAt` | `datetime \| null` | Время завершения фоновой обработки; до неё равно `null`. |
| `status` | `BookingStatus` | Текущее состояние обработки. |

Статусы `BookingStatus`:

| Значение | JSON-значение | Описание |
| :--- | :--- | :--- |
| `Pending` | `0` | Бронь создана и ожидает обработки. |
| `Confirmed` | `1` | Бронь успешно подтверждена. |
| `Rejected` | `2` | При обработке произошла ошибка, бронь отклонена. |

### Эндпоинты броней

| Метод | Эндпоинт | Описание |
| :--- | :--- | :--- |
| **POST** | `/api/events/{eventId}/book` | Создать бронь в статусе `Pending`. Возвращает `202 Accepted`; если свободных мест нет — `409 Conflict`. |
| **GET** | `/api/bookings/{id}` | Получить бронь и её текущий статус. Возвращает `200 OK`. |

Для несуществующего события при создании и для несуществующей брони при получении возвращается `404 Not Found`.
Если все места уже зарезервированы, `POST /api/events/{eventId}/book` возвращает `409 Conflict` с сообщением `No available seats for this event`.

### Фоновая обработка

После создания `BookingsService` сохраняет бронь со статусом `Pending` и сразу резервирует место в модели события. Зарегистрированный `BookingBackgroundService` выбирает до 100 ожидающих броней по возрастанию времени создания и запускает их обработку параллельно через `Task.WhenAll`. Имитация внешних вызовов выполняется параллельно, а запись результатов в хранилища защищена с помощью `SemaphoreSlim(1, 1)`. Для каждой брони он:

1. Проверяет, что событие всё ещё существует. Если оно удалено, бронь отклоняется, а место освобождается.
2. Имитирует обращение к внешнему сервису через `Task.Delay`.
3. При успешной обработке вызывает `booking.Confirm()`.
4. При непредвиденной ошибке вызывает `booking.Reject()` и освобождает место.

Брони в финальном статусе повторно не выбираются.

### Пример использования

Сначала создайте событие и сохраните его идентификатор из ответа:

```http
POST /api/events
Content-Type: application/json

{
  "title": "Summer concert",
  "description": "Open-air concert",
  "startAt": "2026-09-01T18:00:00",
  "endAt": "2026-09-01T21:00:00",
  "totalSeats": 100
}
```

Создайте бронь для полученного `eventId`:

```http
POST /api/events/11111111-1111-1111-1111-111111111111/book
```

Ответ содержит заголовок `Location: /api/bookings/{id}`, время создания и начальный статус `Pending`:

```json
{
  "id": "22222222-2222-2222-2222-222222222222",
  "eventId": "11111111-1111-1111-1111-111111111111",
  "createdAt": "2026-08-12T10:00:00Z",
  "processedAt": null,
  "status": 0
}
```

Проверьте статус по ссылке из `Location`:

```http
GET /api/bookings/22222222-2222-2222-2222-222222222222
```

До завершения фоновой операции ответ содержит `"status": 0`; примерно через 10 секунд при успешной имитации — `"status": 1`.

### Сценарий с попыткой овербукинга

Создайте событие вместимостью в одно место, передав `"totalSeats": 1`, и дважды отправьте запрос бронирования для его `eventId`. Первый запрос зарезервирует единственное место и вернёт `202 Accepted`. Второй запрос не создаст бронь и вернёт `409 Conflict`:

```http
POST /api/events/11111111-1111-1111-1111-111111111111/book
```

```json
{
  "status": 409,
  "detail": "No available seats for this event"
}
```

Таким образом, параллельные и последовательные запросы сверх `totalSeats` не увеличивают число броней и не приводят `availableSeats` к отрицательному значению.

## Формат ошибок

Для необработанных исключений используется единый JSON-формат `ProblemDetails`, основанный на стандарте Problem Details for HTTP APIs (RFC 7807). `ValidationException` возвращается со статусом `400`, остальные необработанные исключения — со статусом `500`. Ошибка также записывается в журнал приложения.

Пример ответа:

```json
{
  "status": 400,
  "detail": "Описание ошибки"
}
```
