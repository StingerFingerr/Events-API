# Events API

REST API для управления событиями и бронированиями на ASP.NET Core (.NET 10). Данные хранятся в PostgreSQL; доступ к ним выполняется через Entity Framework Core и провайдер Npgsql.

## Структура проекта

| Каталог / файл | Назначение |
| :--- | :--- |
| `Events API.csproj` | Presentation: веб-проект, контроллеры, HTTP-маппинг, middleware и DI |
| `Domain/` | Class library: сущности, доменные исключения и константы; без внешних зависимостей |
| `Application/` | Class library: сервисы, DTO, преобразования и интерфейсы репозиториев; зависит только от Domain |
| `Infrastructure/` | Class library: реализации репозиториев, DbContext, конфигурации, миграции и фоновая обработка; зависит от Application и Domain |
| `Test/` | Тесты Application, Domain, фоновой обработки и регистрации DI на InMemory и Moq |
| `Presentation.Tests/` | Тесты HTTP-контроллеров и обработки ошибок |
| `Integration tests/` | Интеграционные тесты репозиториев, транзакций и HTTP API с PostgreSQL |
| `Program.cs` | Composition root: вызовы AddApplication, AddInfrastructure, InitializeDatabaseAsync и запуск HTTP-конвейера |
| `docker-compose.yml` | Локальная база PostgreSQL |
| `dotnet-tools.json` | Манифест локального инструмента `dotnet-ef` |

Presentation подключает Application и Infrastructure. Application зависит от Domain. В Infrastructure находятся EF Core, реализация SHA-256 и выпуск подписанных JWT. Интеграционные тесты запускают веб-приложение через WebApplicationFactory и используют PostgreSQL в Docker.

## Запуск приложения

### Шаг 1. Предварительные требования

Для запуска нужны **.NET SDK 10.0** и работающий сервер **PostgreSQL**. В репозитории настроен PostgreSQL 16 через Docker Compose; для этого варианта также нужен Docker с Compose.

Проверить версию можно командой в терминале:
```bash
dotnet --version
```

### Шаг 2. Клонирование и переход в папку проекта

```bash
git clone <ссылка_на_ваш_репозиторий>
cd "<папка_репозитория>"
```

### Шаг 3. Запуск PostgreSQL

Из корня репозитория запустите базу:

```bash
docker compose up -d postgres
docker compose ps
```

Дождитесь состояния `healthy`. Файл `docker-compose.yml` задаёт базу `eventapi`, пользователя `postgres`, пароль `postgres` и порт `5432`. Данные сохраняются в именованном томе `eventapi_pgdata`. Вместо контейнера можно использовать отдельно установленный PostgreSQL.

### Шаг 4. Настройка строки подключения

В `appsettings.json` задайте `ConnectionStrings:DefaultConnection`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
}
```

Эти значения соответствуют Docker Compose. Для своего сервера измените `Host`, `Port`, `Database`, `Username` и `Password`. Пользователю нужны права на создание и изменение объектов схемы для применения миграций; если база ещё не существует — также права на её создание.

Строку можно переопределить переменной окружения `ConnectionStrings__DefaultConnection`. Пример для PowerShell:

```powershell
$env:ConnectionStrings__DefaultConnection = "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=your_password"
```

### Ключ подписи JWT

Раздел `Jwt` в `appsettings.json` задаёт `Issuer`, `Audience`, `LifetimeMinutes` (60) и `Secret`. Перед запуском задайте секрет длиной не менее 32 байт. Для локальной проверки следующая команда PowerShell 7 создаёт случайный ключ для текущего терминала. Запускайте API из этого же терминала.

```powershell
$env:Jwt__Secret = [Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
```

Для продакшена создайте отдельный случайный секрет и передавайте его из хранилища секретов через `Jwt__Secret`. Все экземпляры API должны использовать одинаковые ключ, издателя и аудиторию. После замены ключа получите новые токены. Значение, ранее сохранённое в истории Git, считайте раскрытым.

### Шаг 5. Сборка и запуск приложения

Из папки решения выполните:

```bash
dotnet restore "Events API.sln"
dotnet build "Events API.sln" --no-restore
dotnet run --project "Events API.csproj" --launch-profile http
```

**Схема БД управляется миграциями EF Core.** После `builder.Build()` приложение вызывает `app.Services.InitializeDatabaseAsync()`: Infrastructure создаёт DI scope, применяет миграции через `MigrateAsync()` и добавляет начальные данные. При запуске автоматически применяются ещё не выполненные миграции. Начальная миграция `InitialCreate` создаёт таблицы `events` и `bookings`, индекс по `bookings.event_id` и внешний ключ `bookings.event_id → events.id` с каскадным удалением. Миграция `AddBookingUser` создаёт таблицу `Users` и внешний ключ `bookings.user_id`. У старых броней владелец может отсутствовать. Миграция `UniqueUserLogin` добавляет уникальный индекс логина. Выполненные миграции учитываются в таблице `__EFMigrationsHistory`.

Для первого запуска с новой базой отдельное применение миграций не требуется. Команды для изменения схемы и ручного применения описаны ниже.

Если таблица событий пустая, приложение добавляет тестовые данные с датами относительно времени запуска (UTC):

| Событие | Начало | Число мест |
| :--- | :--- | :--- |
| Рок-фестиваль | Через 1 день | 100 |
| Конференция .NET | Через 7 дней | 50 |
| Кулинарный мастер-класс | Через 14 дней | 10 |

При непустой таблице повторный запуск эти записи не добавляет. Остановить контейнер с сохранением данных можно командой `docker compose down`.

## Миграции EF Core

Исходники миграций и снимок модели находятся в `Infrastructure/DataAccess/Migrations` и должны сохраняться в репозитории вместе с изменениями моделей. Вместо `EnsureCreated()` используется `Migrate()`; изменения моделей сами по себе не меняют схему — для них нужна новая миграция.

Все команды выполняются из корня репозитория. Сначала восстановите пакеты и локальный инструмент EF Core, версия которого зафиксирована в `dotnet-tools.json`:

```bash
dotnet restore "Events API.sln"
dotnet tool restore
```

После изменения модели или конфигураций создайте миграцию с описательным названием:

```bash
dotnet ef migrations add AddEventLocation --project "Infrastructure/Infrastructure.csproj" --startup-project "Events API.csproj" --output-dir DataAccess/Migrations
```

`AddEventLocation` — пример имени; замените его на название своего изменения. `InitialCreate` уже включена в проект, повторно создавать её не нужно. Проверьте сгенерированные операции `Up` и `Down` перед применением.

Применить все ожидающие миграции вручную:

```bash
dotnet ef database update --project "Infrastructure/Infrastructure.csproj" --startup-project "Events API.csproj"
```

Команда использует `ConnectionStrings:DefaultConnection`; базу PostgreSQL нужно предварительно запустить. При обычном запуске API тот же результат достигается автоматически через `InitializeDatabaseAsync()`.

Показать список миграций и проверить, нет ли изменений модели без миграции:

```bash
dotnet ef migrations list --project "Infrastructure/Infrastructure.csproj" --startup-project "Events API.csproj"
dotnet ef migrations has-pending-model-changes --project "Infrastructure/Infrastructure.csproj" --startup-project "Events API.csproj"
```

Получить SQL для просмотра или отдельного применения:

```bash
dotnet ef migrations script --project "Infrastructure/Infrastructure.csproj" --startup-project "Events API.csproj" --output migrations.sql
```

### База, созданная прежней версией приложения

Ранее приложение использовало `EnsureCreated()` и таблицы `Events` и `Bookings`. Такая база не содержит истории миграций и автоматически не преобразуется в текущую схему `events` / `bookings`. Для локального запуска можно указать новую пустую базу через строку подключения. Если существующие данные нужно сохранить, сначала сделайте резервную копию и подготовьте отдельный перенос данных и согласование схемы; повторный запуск `InitialCreate` не выполняет этот перенос.

## Проверка через Swagger

Откройте [Swagger UI](http://localhost:5002/swagger/index.html). Маршруты доступны также с префиксом `/api`. Для каждого запроса нажмите **Try it out**, заполните поля и нажмите **Execute**. [Спецификация OpenAPI](http://localhost:5002/swagger/v1/swagger.json)

1. В `POST /auth/register` передайте `{"login":"visitor","password":"test-visitor-pass"}`. Успешная регистрация возвращает `201`. Роль по умолчанию — `User`. Если такой логин уже занят, получите `409`.
2. В `POST /auth/login` отправьте те же данные. Скопируйте значение поля `token` из ответа `200`.
3. Пока токен не введён, выполните `POST /events` с данными события из примера ниже. Ожидается `401`. Нажмите **Authorize**, вставьте токен без кавычек и без префикса `Bearer`, затем нажмите **Authorize → Close**. Повторите создание события. Для роли `User` ожидается `403`.
4. Зарегистрируйте второй логин с паролем и полем `"role":"Admin"`. Получите токен через `POST /auth/login`. В окне **Authorize** нажмите **Logout** и введите токен администратора.
5. Выполните `POST /events` с уникальным названием и будущими датами UTC. Скопируйте `id` события из ответа `201`. В `POST /events/{eventId}/book` подставьте этот идентификатор. Из ответа `202` возьмите **id брони** и передайте его в `DELETE /bookings/{id}`. Ожидается `200` и `status: 3` (`Cancelled`). Повторная отмена возвращает `409`.

Пример тела для создания события (обновите даты перед запуском):

```json
{"title":"Swagger concert","description":"Live music","startAt":"2030-09-01T18:00:00Z","endAt":"2030-09-01T21:00:00Z","totalSeats":10}
```

## Роли и маршруты

| Метод и маршрут | Доступ | Успешный ответ |
| --- | --- | --- |
| `POST /auth/register`, `POST /auth/login` | Открытый | `201` и ID пользователя при регистрации, `200` и JWT при входе |
| `GET /events`, `GET /events/{id}` | Открытый | `200` |
| `POST /events` | Admin | `201` |
| `PUT /events/{id}`, `PATCH /events/{id}`, `DELETE /events/{id}` | Admin | `200` при изменении, `204` при удалении |
| `POST /events/{eventId}/book` | User и Admin | `202` и заголовок `Location` |
| `GET /bookings/{id}`, `DELETE /bookings/{id}` | Владелец или Admin | `200` и текущее состояние брони |

В учебной конфигурации публичная регистрация принимает роль `Admin` для проверки прав. Перед публичным развёртыванием ограничьте назначение этой роли. Пароли в этой версии хешируются SHA-256 по условиям задания. Для production используйте специализированное хеширование паролей с солью. JWT подписывается HS256 и содержит ID пользователя (`sub`), логин (`unique_name`) и роль (`role`). API проверяет подпись, издателя, аудиторию и срок действия.

## Запуск тестов

В решении три тестовых проекта:

| Проект | Что проверяет | Требования |
| :--- | :--- | :--- |
| `Test/Test.csproj` | Сервисы, модель брони, регистрацию DI и фоновую обработку; использует EF Core InMemory и Moq | .NET SDK 10; Docker и PostgreSQL не нужны |
| `Presentation.Tests/Presentation.Tests.csproj` | Контроллер броней и HTTP-маппинг исключений; ссылается на веб-проект | .NET SDK 10; Docker и PostgreSQL не нужны |
| `Integration tests/Integration tests.csproj` | Репозитории, конкурирующие транзакции и полный HTTP-сценарий регистрации, входа, проверки прав и брони | .NET SDK 10 и работающий Docker с Linux-контейнерами |

Тесты InMemory создают отдельную базу для каждого экземпляра тестового класса. Scoped-сервисы и репозитории получают зависимости из DI; параллельные запросы бронирования используют отдельные scope. Для поиска событий в этих тестах зарегистрирована тестовая реализация `InMemoryEventRepository`, поскольку PostgreSQL-функция `ILIKE` не поддерживается InMemory. Эти тесты проверяют сохранение между контекстами и защиту от превышения вместимости, но не SQL и ограничения PostgreSQL.

Интеграционные тесты автоматически запускают **один общий контейнер PostgreSQL `16-alpine`** на свободном порту и удаляют его после завершения. Классы входят в одну коллекцию xUnit и выполняются последовательно. Перед каждым тестом, включая каждый вариант `[Theory]`, вызываются `EnsureDeletedAsync()` и `MigrateAsync()`: база очищается и схема создаётся из миграций. Данные готовятся в каждом тесте самостоятельно, поэтому порядок запуска не влияет на результат.

Проверяются все сочетания фильтров событий, границы дат, регистронезависимый поиск, сортировка, пагинация и общее количество результатов, перечитывание сущностей, выборка ожидающих броней, сохранение статусов, внешний ключ, каскадное удаление и откат при ошибке вставки. Строка подключения получается из контейнера: тесты не используют базу приложения, а запуск Docker Compose для них не требуется. При первом запуске Docker загружает необходимые образы, поэтому нужен доступ к реестру образов.

Для запуска всех тестов из корня репозитория **сначала запустите Docker**:

```bash
dotnet test "Events API.sln"
```

Только тесты InMemory (без Docker):

```bash
dotnet test "Test/Test.csproj"
dotnet test "Presentation.Tests/Presentation.Tests.csproj"
```

Только интеграционные тесты:

```bash
dotnet test "Integration tests/Integration tests.csproj"
```

Для проверки повторяемости выполните последнюю команду дважды. Дополнительные сведения — в [README интеграционных тестов](Integration%20tests/README.md).

## Получение списка событий: фильтрация и пагинация

Эндпоинт `GET /api/events` поддерживает следующие необязательные query-параметры:

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `title` | string | Поиск событий, в названии которых содержится указанная строка. Регистр не учитывается. |
| `from` | datetime | Нижняя граница даты начала: возвращаются события с `startAt >= from`. |
| `to` | datetime | Верхняя граница даты начала: возвращаются события с `startAt <= to`. |
| `page` | int | Номер страницы от `1` до `100`; по умолчанию — `1`. |
| `pageSize` | int | Число элементов на странице от `1` до `100`; по умолчанию — `10`. |

Фильтры можно комбинировать. После фильтрации события сортируются по возрастанию даты начала, затем применяется пагинация.

Пример запроса:

```http
GET /api/events?title=festival&from=2027-08-01T00:00:00Z&to=2027-08-31T23:59:59Z&page=1&pageSize=5
```

Ответ содержит список `items` и метаданные пагинации: `page`, `pageSize`, `totalItems`, `totalPages`.

## Модель события

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `guid` | Уникальный идентификатор события. |
| `title` | `string` | Название события. |
| `description` | `string \| null` | Необязательное описание события. |
| `startAt` | `datetime` | Дата и время начала события. |
| `endAt` | `datetime` | Дата и время окончания события. |
| `totalSeats` | `int` | Общая вместимость события. При создании должна быть больше нуля. |
| `availableSeats` | `int` | Число ещё доступных для бронирования мест. При создании равно `totalSeats`, уменьшается при резервировании и не передаётся клиентом в запросах. |

При изменении `totalSeats` через `PUT /api/events/{id}` уже зарезервированные места сохраняются: `availableSeats` пересчитывается с учётом новой вместимости. Нельзя установить вместимость меньше числа уже зарезервированных мест.

### Правила запросов

В `POST` и `PUT` передаются `title`, `startAt`, `endAt`, `totalSeats` и необязательное `description`. В `PATCH` передаётся только `title`. Во всех трёх случаях DTO и сервис проверяют, что название не пустое, не состоит только из пробелов и содержит не менее 5 символов. PostgreSQL ограничивает название 200 символами, описание — 500; превышение этих ограничений сейчас приводит к ошибке сохранения (`500`), отдельная HTTP-валидация максимальной длины не настроена.

Дата начала не должна быть в прошлом, дата окончания должна быть позже начала, а вместимость — больше нуля. Передавайте даты в UTC в формате ISO 8601 с суффиксом `Z`, включая параметры `from` и `to`: в PostgreSQL используется `timestamp with time zone`.

При создании события и изменении названия через `PATCH` сервис проверяет совпадение полного названия без учёта регистра и возвращает `409` при совпадении. При полном обновлении через `PUT` такая проверка сейчас не выполняется; уникальный индекс по названию в БД отсутствует.

Для изменения только названия используйте:

```http
PATCH /api/events/11111111-1111-1111-1111-111111111111
Content-Type: application/json

{
  "title": "Updated concert title"
}
```

## Бронирование и отмена

Владелец новой брони определяется по `sub` из JWT. Каждая бронь занимает одно место. DTO содержит `id`, `eventId`, `createdAt`, `processedAt` и `status`. PostgreSQL хранит статус строкой, API передаёт его числом.

| Статус | JSON | Учитывается в лимите |
| --- | --- | --- |
| Pending | 0 | Да |
| Confirmed | 1 | Да |
| Rejected | 2 | Нет |
| Cancelled | 3 | Нет |

Один пользователь может иметь до 10 активных броней суммарно по всем событиям. При отмене активной брони освобождаются место на событии и позиция в лимите пользователя. Запись сохраняется со статусом `Cancelled`. Удаление самого события каскадно удаляет его брони.

Создание и отмена выполняются в транзакции PostgreSQL уровня `Serializable`. Это защищает остаток мест и лимит при одновременной работе нескольких экземпляров API. Конфликт конкурентного изменения возвращает `409`. Внутри процесса операции также координирует семафор.

Фоновая служба выбирает до 100 броней `Pending` по времени создания. После имитации внешнего вызова (1 секунда) обработчик перечитывает каждую бронь в отдельном scope. Если статус всё ещё `Pending`, он подтверждает бронь и сохраняет время обработки. При отсутствии работы следующий опрос происходит через 100 мс.

## Ответы при ошибках

| HTTP | Когда возвращается |
| --- | --- |
| 400 | Неверные данные запроса или попытка забронировать уже начавшееся событие |
| 401 | Неверный логин или пароль при входе, отсутствующий, недействительный или просроченный токен при доступе к защищённому ресурсу |
| 403 | Недостаточная роль или попытка обычного пользователя прочитать либо отменить чужую бронь |
| 404 | Событие или бронь не найдены |
| 409 | Логин занят, нет свободных мест, достигнут лимит активных броней, бронь уже отменена или возник конфликт записи |
| 500 | Необработанная ошибка сервера |

Для исключений middleware формирует `ProblemDetails` с полями `status` и `detail`. Ошибки проверки DTO имеют поля `message` и `errors`. Отказы JWT middleware могут иметь пустое тело.

## Решение проблем при запуске

| Симптом | Что проверить |
| :--- | :--- |
| `dotnet ef` не найден | Выполните `dotnet tool restore` из корня репозитория, где находится `dotnet-tools.json` |
| API не подключается к PostgreSQL | Проверьте `docker compose ps`, состояние `healthy`, порт `5432` и строку подключения; журнал БД доступен через `docker compose logs postgres` |
| Порт `5432` занят | Освободите порт или измените опубликованный порт в Compose и `Port` в строке подключения |
| Интеграционные тесты не подключаются к Docker | Запустите Docker, включите Linux-контейнеры и проверьте `docker version`; при первой загрузке образов проверьте доступ к реестру |
| Миграция завершается ошибкой на старой базе | Проверьте, была ли база создана через `EnsureCreated()`, и прочитайте раздел о переходе выше |
| Ошибка сохранения даты | Проверьте, что дата передана в UTC с суффиксом `Z` |
